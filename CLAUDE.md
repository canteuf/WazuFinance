# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Wazu Finance** — multi-user budget tracking app. React Native + Expo (SDK 57, TypeScript strict) + Supabase (Postgres, Auth, RLS, Realtime). The full French-language spec is [spec-app-budget.md](spec-app-budget.md); it is the source of truth for features, data model, and V1 scope.

## Commands

```bash
npm start                # expo start
npm run android          # expo start --android
npm run web              # expo start --web
npm run lint             # expo lint (eslint-config-expo)
npx tsc --noEmit         # typecheck
npm test                 # jest-expo — modules purs uniquement (money, dates, erreurs)

npm run test:db          # pgTAP tests — needs Docker Desktop running + `npx supabase start`
npx supabase start       # local stack: applies all migrations from scratch
npx supabase stop
npx expo export --platform android --output-dir <dir>   # bundle check, no device needed

npx supabase db push                # apply pending migrations to the linked project
npx supabase migration list --linked  # compare local vs remote migration state
npm run db:types                    # regenerate src/types/database.ts from the linked project

eas build -p android --profile preview   # installable APK, built by EAS (global eas-cli)
eas update --channel preview --message "…"   # ship JS-only changes to installed preview APKs
```

The project is linked to Supabase ref `ozwltxywsqvgmefuqvfv`. Migration files must keep the CLI's `<14-digit timestamp>_name.sql` naming or `db push` skips them.

`.github/workflows/ci.yml` runs tsc, lint and Jest, and applies every migration to an empty database before running the pgTAP suite, on each push to `main` and each pull request.

Database tests are pgTAP files under `supabase/tests/`, run against the local stack. `npm test` (Jest) covers only framework-free modules under `src/lib/` — no component or hook has a JS test yet.

`handle_new_user()` runs inside Supabase Auth's signup transaction; when it fails the client only sees an opaque `Database error saving new user`. Any change to `users`, `budget_groups`, or `account_memberships` must be re-run against `npm run test:db`.

Requires `.env` (copy from `.env.example`) with `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY`. [src/lib/env.ts](src/lib/env.ts) throws at startup if either is missing. Env vars are inlined at build time — after editing `.env`, restart with `npx expo start --clear`.

## Expo version discipline

Per [AGENTS.md](AGENTS.md): read <https://docs.expo.dev/versions/v57.0.0/> before writing Expo code. SDK 57 / expo-router v6 / React 19.2 APIs differ from older tutorials — notably `Stack.Protected guard={…}` for route guarding.

**Never run `npm audit fix --force`.** npm resolves an advisory by picking whatever version falls outside the vulnerable range, regardless of the SDK: on 2026-09-10 it downgraded `expo` to 46 and `expo-router` to 5 — eleven majors back — and the app could no longer start. Align versions with `npx expo install --fix` only. The moderate advisories `npm audit` reports come from two packages pulled in by the SDK itself (`decode-uri-component` through react-navigation, `uuid` through Expo's tooling); they have no npm-side fix that keeps SDK 57, and they go away when Expo ships patch releases, which `npx expo install --fix` picks up.

If `npx expo install --fix` fails with `EALLOWSCRIPTS` ("--allow-scripts is not allowed in project-scoped installs"), the user-level `~/.npmrc` holds an `allow-scripts` line that npm 11.19 rejects when Expo spawns the install. Don't edit the user's global config: run `npx expo install --check` and `npm install` the exact versions it lists — same result.

Windows: if `npm ci` or `npm install` fails with `EPERM` on `@unrs/resolver-binding-win32-x64-msvc/*.node`, VS Code's ESLint server has that native module loaded. Run "ESLint: Restart ESLint Server" or move the folder out of `node_modules` — never kill the VS Code extension host, which Claude Code runs inside.

## Native build (EAS)

**The three profiles in `eas.json` pin `"node": "22.20.0"`, and that pin is load-bearing.** `@supabase/supabase-js` and its five sub-packages declare `engines.node >= 22`; react-native declares `^20.19.4 || ^22.13.0 || ^24.3.0`. The intersection starts at 22.13. The build worker otherwise defaults to Node 20, where `npm ci` fails hard on the engine conflict — in about fifteen seconds, and the build log shows only `npm ci --include=dev exited with non-zero code: 1`, never the engine mismatch itself. Any new dependency raising its Node floor has to be checked against this pin.

**`eas-cli` is installed globally, never as a project dependency.** EAS runs `npm ci --include=dev` on the worker, so a dev dependency ships 344 packages to a machine that has no use for them. `cli.version` in `eas.json` already enforces the version. Removing it from `devDependencies` also removes the local `eas` binary, so `npx eas` stops resolving — the package is named `eas-cli`, and the bare `eas` command comes from the global install.

Installing the resulting APK needs `adb` from the Android platform-tools. Without it the build still succeeds; only the automatic install step fails, with `spawn adb ENOENT`, and the APK stays downloadable from the build URL.

Windows PATH: `[Environment]::SetEnvironmentVariable("Path", $env:Path + ";…", "User")` is a trap. `$env:Path` holds the *merged* machine + user PATH, so each call copies the machine PATH into the user PATH. Past 2047 characters in a `REG_SZ` key, Windows silently stops merging the user PATH altogether and every globally installed tool disappears from new sessions. Read the user scope explicitly instead — `[Environment]::GetEnvironmentVariable("Path", "User")` — and keep the key `REG_EXPAND_SZ`. VS Code also hands each terminal the environment it captured at its own launch, so a PATH change needs VS Code itself restarted, not just a new terminal tab.

## Database backups and keep-alive (GitHub Actions, private repo)

The Supabase free plan offers no downloadable backup and pauses a project after 7 days without activity. Two workflows cover both, at no cost — **in the private repository `canteuf/WazuFinance-ops`, not in this one.** This repository is public, and on a public repository any GitHub account can download a workflow's artifacts: until 2026-09-29 the nightly dumps (whole database, `auth.users` with password hashes included) sat here behind a single passphrase. Never add a workflow that uploads data, or that holds a database secret, to this repository.

- `db-backup.yml` — nightly at 02:00 UTC (and on demand): `supabase db dump` for roles, schema and data, tarred, encrypted for a GPG **public key** (secret `BACKUP_PUBLIC_KEY`; the private key lives offline only), uploaded as a 30-day artifact. It uses the Supabase CLI rather than the runner's `pg_dump`, which is older than the server (Postgres 17) and refuses to dump it. It fails if `data.sql` holds no `COPY "public"."transactions"`, so an empty dump never passes for a success. Key creation and restore are in that repository's README.
- `db-keepalive.yml` — every two days at 06:00 UTC: one real SQL query through `psql`.

Both read the `SUPABASE_DB_URL` secret of that repository, the **Session pooler** connection string (dashboard → Connect), percent-encoded: the direct connection is IPv6-only on the free plan and GitHub runners are IPv4-only. The CLI version in `db-backup.yml` follows this project's (`npx supabase --version`), like `ci.yml`. Third-party actions there are pinned by commit SHA: `supabase/setup-cli@v1` is a branch, and that action receives full database access.

Audits and other internal notes also go to that repository: `docs/` here is published by GitHub Pages.

## App icons

`app.json` wires four generated files from `assets/images/`, and Android composes three of them itself rather than taking a finished square.

- `android-icon-foreground.png` — the glyph alone on transparency. Android masks the icon to the launcher's shape (circle, squircle, teardrop), so the drawing has to stay inside the central ~66 %: here 560 × 436 on a 1024 canvas. A full-bleed icon used as the foreground gets its corners cut.
- `android-icon-background.png` — opaque, edge to edge, **no border and no rounded corners**. A hairline border there reads as a stray line once the mask is applied.
- `android-icon-monochrome.png` — the same silhouette in flat white, for Android 13+ themed icons, which recolour it against the wallpaper.
- `icon.png` — the flattened squircle, for iOS and the web. `app.json` deliberately has no `ios.icon`: the template's value pointed at an Icon Composer bundle (`assets/expo.icon`) holding the Expo logo, which would have shipped as the iOS icon.

**An app icon is judged at 48 dp, not at 1024.** The original artwork put a mid-green glyph on a dark-green field — 3.4:1, which dissolves in the launcher. The shipped background is `#062019`, giving 6.89:1. Any new artwork should be checked by compositing foreground over background, masking to a circle and downsampling to 48 px before it is accepted.

The splash screen shares that background colour; `imageWidth` is 140 because the W is much wider than tall, where the Expo template's 76 suited its own square logo.

## Architecture

Routes live under `src/app/` (expo-router, `src/` root configured via `tsconfig` path alias `@/*`).

```text
src/app/_layout.tsx        AuthProvider + Stack.Protected session guard
src/app/(auth)/            sign-in, sign-up  — reachable only when session === null
src/app/(app)/             reachable only when session !== null
src/app/(app)/(tabs)/      Synthèse, Budgets, Opérations, Épargne — the four tab roots
src/app/(app)/*.tsx        everything else, stacked or as a form sheet above the tabs
src/lib/supabase.ts        client, AsyncStorage persistence, AppState auto-refresh
src/providers/             AuthProvider (session state + signIn/signUp/signOut)
supabase/migrations/       schema, RLS policies, seed — apply in numeric order
```

**Password reset uses an emailed code, not a link** (`(auth)/forgot-password.tsx`): `resetPasswordForEmail()`, then `verifyOtp({ type: 'recovery' })` and `updateUser()`. The project's « Reset password » email template must show `{{ .Token }}` — `supabase/templates/recovery.html`, wired in `config.toml` for the local stack, to be pasted in the dashboard for the hosted one. Its logo is `docs/email/logo.png` (96 px, served by GitHub Pages): an e-mail can neither attach a file nor show a base64 image, which Gmail blocks, so any image in a template must be a public `https://` URL. The verified code opens a session at once; `AuthProvider` holds it back (`recovering`) until the new password is saved, otherwise the guard would unmount the screen mid-flow.

**Navigation never redirects manually after auth.** `signIn`/`signUp` only call Supabase; `onAuthStateChange` updates the provider, and the `Stack.Protected` guards in the root layout swap route groups. Adding a `router.replace()` after login fights the guard.

Neither auth route is named `index`, so `(app)/(tabs)/index.tsx` owns `/` without a route conflict — route groups in parentheses don't appear in URLs.

The account settings screen is reached from `AccountButton`, placed in each tab's own header rather than in a navigator-managed header: the four tab screens handle their top safe area differently (a virtualised list for history, a `ScrollView` elsewhere), and a shared header would have forced all of them to give it up. Typed routes (`.expo/types/router.d.ts`) are regenerated by the dev server, not by `expo export` — after adding a route, `tsc` rejects links to it until `npx expo start` has run once.

## Core data model decision

**A personal account is a `budget_group` with `is_personal = true` and a single member.** There is no separate "personal" table or code path. All access flows through `account_memberships`, so one set of RLS policies covers personal and shared budgets. Do not introduce a parallel personal-account model.

The `handle_new_user()` trigger on `auth.users` creates profile + personal group + `owner` membership in the signup transaction, so the app never sees a user without a group. `account_memberships_guard_personal` enforces the one-member invariant.

Tables: `users`, `budget_groups`, `account_memberships`, `categories` (`group_id IS NULL` = read-only global default), `transactions`, `budgets`, `savings_goals`, `recurring_transactions`, `debts`, `wallets`, `wallet_transfers`, `group_invitations`, `invitation_attempts` and `applied_requests` (functions only), `activity_log` and `former_members` (written by triggers only — see below).

**Default categories include the CFA zone's own spending** (migration `20260925000300_regional_categories.sql`): Tontine, Famille, Crédit & data, Eau & électricité, Frais mobile money, Cérémonies, Dons & église, Dettes; income Commerce, Transfert reçu, Tontine reçue. « Achat de stock » (expense) came with `20260928000200_real_usage.sql`: with « Commerce » it feeds `commerce_summary()` (sales, stock, margin, summed in Postgres), whose card `CommerceEntry` shows on the Synthèse only when the period holds one of those operations — no setting. It matches both categories **by name**, default or the group's own homonym, and `commerce_category()` picks the group's own « Commerce » first. Defaults are only ever added, never removed — transactions and budgets reference them. A default added after the fact can collide with a custom category a group already created under the same name, which `categories_guard_homonym` never checks (it skips `group_id IS NULL`); `listForGroup()` runs `hideShadowedDefaults()` so the group's own category wins and the grid shows one tile. A new default icon goes into `BY_ICON` in `category-colors.ts`, and must not appear in `category-icons.ts`.

**Custom categories are created in place, under the grid** (`CategoryCreator`, in both the transaction and the envelope form), never in a sheet of their own: the transaction form is already a `formSheet`. The new category goes into the group's cache through `setQueryData` before any refetch, because `TransactionForm` drops a selection missing from the list. A name is unique per group and type, case-insensitively, *and* against the defaults: the two partial unique indexes can't see each other, so `categories_guard_homonym` checks both scopes and raises `P0001`, whose message the app shows verbatim. The icons in `category-icons.ts` deliberately exclude every seed icon, because `categoryTone()` colours the defaults by icon, and a custom category using `gift` would take the colour of « Cadeau ».

**The budget period is not the calendar month.** `budget_groups.period_start_day` (1–28, `check`-constrained) sets the day a period starts, so a budget can follow the payday. It sits on the group, not the user, so both members of a shared budget see the same figures — and `budget_groups_update_owner` already restricts who can change it. The 28 cap exists because the 29th, 30th and 31st don't occur every month. Bounds are computed client-side by `periodBounds()`: the server is UTC, and `date_trunc('month', now())` reports the wrong period during the first hours of a rollover day.

**The currency is the CFA franc, which has no minor unit (ISO 4217 exponent 0).** [src/lib/money.ts](src/lib/money.ts) is its only definition: `CURRENCY_SYMBOL`, `formatMoney()` (amount + non-breaking space + symbol), `spokenAmount()` for accessibility labels, and integer-only `parseAmount()`. The symbol is **« FCFA »**, not the ISO code: XAF is Central Africa only, and an Ivorian user (XOF, same value) read a foreign currency; FCFA is what price tags and mobile money apps print for both zones. Amount inputs hold bare digits (what `parseAmount` reads) and display them grouped by thousands through `groupDigits()` / `amountDigits()` (`AmountInput`), so 150 000 and 1 500 000 no longer look alike. Any amount shown to TalkBack goes through `spokenAmount()` — a number next to a separate « FCFA » Text is read as the number, then F-C-F-A spelt out. The app enters and displays whole amounts, with no decimals and a `number-pad` keyboard; the columns stay `numeric(12,2)` and hold integers, so there was no migration. A screen never writes `€`, `XAF` or `FCFA` itself — it goes through `money.ts`, so the code changes in one place. Amounts saved before the switch (in euros, possibly with decimals) were not converted: they keep their value, read as francs CFA, and are rounded on display and in the edit field.

## Profile avatars

**`users.avatar` holds an id (`a01`–`a17`) of an image shipped in `assets/avatars/`, never an upload; `NULL` means initials.** No photo to host, moderate or send through the database, and the app draws the same face on every device. `MemberAvatar` is the one place that draws a person; it takes the raw column value and `parseAvatarId()` turns any id this version doesn't know — an avatar added by a newer app, a corrupted value — into initials rather than a broken image.

The images are generated once by `scripts/gen-avatars.mjs` (DiceBear Avataaars rasterised to PNG by resvg). DiceBear and resvg are deliberately not dependencies: EAS runs `npm ci --include=dev`, and the script only matters when adding an avatar. Each preset fixes every visible attribute instead of a seed, so an id keeps drawing the same face whatever the library version does, and skin tones are spread on purpose. **Ids are append-only** — an id is stored in profiles, and editing a preset would change someone's face under their eyes. To add one: a `PRESETS` line, regenerate, then `AVATAR_IDS` in `src/lib/avatars.ts` and `AVATAR_SOURCES` in `src/components/ui/avatar-sources.ts` (`tsc` fails if the two disagree; a Jest case checks every id has its file).

The database constrains the format (`users_avatar_format`, `^a[0-9]{2}$`), not the list, so adding an avatar needs no migration. The column has its own `grant update (avatar)`, like `display_name`. Other members read it through `users_select_self_or_covisible`, which is what puts faces on the member stacks. `group_overviews()` returns `member_avatars` as an array parallel to `member_names` — same join, order and limit — and `pairMembers()` zips them; an avatar-less member is a `NULL` in the array, not a gap.

## Security & monitoring

**The Supabase session lives in SecureStore** (`src/lib/secure-session-storage.ts`, Keystore on Android, Keychain on iOS), split into 500-character chunks because Android caps a SecureStore value around 2 KB and a session exceeds it. The chunks alternate between two key sets (`.a.N` / `.b.N`) and a `.slot` pointer (`a:5`) is flipped last in a single write, so a write killed at any point leaves either the old session or the new one, never a mix (`src/lib/chunked-storage.ts`, Jest). The earlier format (`.count` + chunks rewritten in place) is still read, and replaced at the next write. A session left in clear in AsyncStorage by an older build is copied over once, then deleted, so updating signs nobody out. The value is cached in memory after the first read: supabase-js reads storage before every request. **Don't reintroduce `expo-crypto`'s AES for this**: it was tried and dropped — on Android `AESSealedData.fromCombined()` throws on the base64 string its docs accept, and decryption returned extra bytes, which corrupted the session and signed the user out on every launch. `android.allowBackup` is `false`, so neither AsyncStorage (query cache included) nor SecureStore reaches Google backups; the query cache itself stays in clear inside the app sandbox.

**App lock** (`AppLockProvider`, mounted in `(app)/_layout.tsx` outside every other provider): off by default, turned on from Paramètres → « Verrouillage de l'app ». A 4-digit code, stored only as a salted SHA-256 in SecureStore under `app_lock_<userId>` (per account, per device, never synced), plus fingerprint/face through `expo-local-authentication` when the phone has one enrolled. It locks on cold start and when the app returns after `LOCK_AFTER_MS` (one minute) in the background; `inactive` doesn't count. The lock screen is an RN `Modal`, not a view over the stack, because a `formSheet` is presented above the stack and would stay visible. Failures persist across restarts: free for four, then 30 s / 1 min / 5 min / 15 min, and the tenth signs out locally and clears the lock (`src/lib/app-lock.ts`, Jest). « Code oublié » does the same after a confirmation — the account password is the way back. Changing or disabling the code re-asks the current one through the same `checkPin` counter, otherwise the setup screen would be a guessing oracle. `signOut({ local: true })` exists for these paths, which must work offline.

**Crash reporting** (`src/lib/monitoring.ts`, Sentry): on only outside `__DEV__` and when `EXPO_PUBLIC_SENTRY_DSN` is set — for EAS builds, as an EAS environment variable, since `.env` is not uploaded. It sends the error, the device and the user id (never the email), with `sendDefaultPii: false`; touch and console breadcrumbs are dropped (accessibility labels carry amounts) and request URLs lose their query string (note search and filters travel there). Every event then goes through `scrubEvent()` (`src/lib/error-scrub.ts`, Jest) in `beforeSend`: a Supabase error is a plain object, which Sentry attaches whole as `extra.__serialized__`, and Postgres writes the refused row into `details` (« Failing row contains (…, 1500, Marché) »). `extra` is dropped and messages lose the row, key and input values. The privacy policy promises this; a new way of reporting errors must keep it true. `reportError()` is for errors the app recovers from silently. The Sentry Expo config plugin is deliberately **not** in `app.json`: it uploads source maps at build time and needs `SENTRY_AUTH_TOKEN`; without the plugin, native and JS crashes are still reported, with minified JS stacks. Adding it later means the plugin entry plus that secret in EAS.

**Over-the-air updates** (`expo-updates`, EAS Update): each build profile has a `channel` in `eas.json`; `runtimeVersion` follows `appVersion`, so **any change to native code (a new native module, an `app.json` plugin) needs `version` bumped in `app.json` and a new build** — otherwise an update would load JS expecting a native module the APK lacks. Updates download in the background at launch and apply at the next cold start. Expo Go ignores them.

## Legal texts, consent and retention

The terms (`docs/legal/cgu.html`), privacy policy (`confidentialite.html`) and account-deletion page (`suppression.html`, the URL Google Play asks for) are published by GitHub Pages; `src/lib/legal.ts` holds their URLs and `TERMS_VERSION`, the entry-into-force date printed on both texts. **The policy describes what the code does — change one, change the other.**

- **Consent** lives in `user_metadata.terms_version`, no table: sign-up writes it with the account (the consent checkbox, with the 18+ statement), and `acceptTerms()` writes it for older accounts. `TermsGate`, a RN `Modal` in the `(app)` layout, blocks a session whose version differs — **online only**, since accepting needs the network and the app must stay usable offline. Bumping `TERMS_VERSION` re-asks everyone, as the policy promises for important changes.
- **Retention is enforced, not just announced**: `purge_expired_data()` (migration `20260929000200`, pg_cron nightly at 03:30 UTC) deletes activity-log entries after 24 months, invitation attempts after 1 day, applied request ids after 30 days, dead invitations 30 days after expiry, product events after 13 months, and the account-deletion registry after 35 days. A new kind of stored data needs its line there and in section 7 of the policy.
- **`account_deletions`** records the id of every deleted `users` row (trigger, so dashboard deletions count too), so deletions can be re-applied after restoring a backup; the procedure is in the WazuFinance-ops README.
- **Product events** are two, `app_opened` and `invite_shared`, through `log_product_event()` (once per user, type and day; no client privilege on the table). Sign-ups, first operations and group joins are read from their own tables' `created_at`, never logged twice. `logProductEvent()` never throws. The queries are in the WazuFinance-ops README.
- **`export_my_data()`** (Paramètres → Mes données) returns the personal group whole, the user's own rows in shared groups and their savings goals, as JSON — `SECURITY INVOKER`, so it can never return more than the caller already reads. A new user-data table belongs in it.
- **Onboarding** (`OnboardingGate`, a RN `Modal` after `TermsGate`): usage (personal / family / commerce / tontine), payday (sets the personal group's `period_start_day`), mobile money wallets to tick (unticked by default, ids drawn once so a retry after a lost response finds them — a `23505` counts as created). Only accounts whose sign-up wrote `user_metadata.onboarding_pending: true` see it, so accounts older than this version never do; `completeOnboarding()` sets it false and stores `usage`, which the privacy policy lists. Online only, like `TermsGate`. It ends by opening the first entry.
- **The dashboard hides empty secondary cards** (`useDashboardSections()`): wallets until a second wallet exists, budgets, savings and debts until they hold something. `DiscoverMore` (« Aller plus loin ») lists the hidden ones, plus « Partager un budget » while the user has no shared group — first when the declared usage is family or tontine. A card still loading or in error stays visible: hiding existing data is worse than one card too many.
- Exported files all start with `wazu-`; `clearExportedFiles()` deletes them on every `SIGNED_OUT`. They are not deleted right after sharing: Android's `shareAsync` returns before the target app has read the file.

## Data access layers

`screens → hooks → src/data/ → supabase`, one-way dependencies. A screen never imports `supabase` directly; `src/data/` never imports React. TanStack Query holds the cache; keys all live in `src/lib/query-keys.ts`.

Invalidating a key only reaches keys it's a prefix of, never the other way round. Invalidate `queryKeys.transactions()` (the root) to reach both the recent list and the detail records; invalidating a leaf like `recentTransactions(groupId)` leaves an open detail record stale. Always invalidate by the widest prefix the mutation affects.

Every read on the dashboard shares one set of bounds from `periodBounds()`: `period_summary` for the current period, the same function again for the previous one (the comparison), `category_breakdown` for the split, and `listRecent` for the list. Deriving bounds separately in a component is how the headline total and the bars start describing different periods.

`listRecent` takes its bounds as required arguments for that reason. An unbounded recent list put last period's rent under "Solde de septembre", and the row then vanished when the user tapped "Tout voir" — the history opens on `DEFAULT_FILTERS`, whose period is the current one. Both ends now agree, so "Tout voir" only ever widens the set.

`category_breakdown` inner-joins `categories`, so uncategorised expenses are absent from it while still counting in `period_summary().expense`. Bar proportions are therefore computed against the sum of the slices, never against `expense` — otherwise the bars never reach 100%.

Budgets read through `category_breakdown` rather than their own aggregate: the
RPC already defines "spend for the period", and a second definition alongside
it would be one more thing to keep in agreement. The client only matches by
`category_id` and divides — the summation stays in Postgres. `budget-progress.ts`
holds the thresholds and the sort order, so they are covered by Jest rather
than buried in JSX. The one exception is the summary card's grand total: `budget_totals()` sums ceilings and budgeted-category spend in Postgres, with the same spend definition as `category_breakdown`. Its key `budgetTotals` nests under `['transactions']` (spend comes from there), and budget mutations and the budgets Realtime hook invalidate `budgetTotalsAll()` as well.

**Budget ceilings and savings amounts are never rewritten, only adjusted.** `adjust_budget_amount()` and `add_to_savings_goal()` add a signed delta in a single `update … set x = x + delta`, so two members adjusting the same envelope (or two devices depositing on the same goal) both count. The same gesture sent twice counts once: both take an app-drawn `p_id` (`useRequestIds()`, one per sheet and amount). For a deposit it becomes the savings transaction's id; for a ceiling, `claim_request()` records it in `applied_requests` (no client privilege, 30-day purge), and a refused adjustment rolls the mark back with it. There is deliberately no data function that writes `budgets.amount` or `savings_goals.current_amount` directly after creation; `UpdateSavingsGoalInput` has no amount field for that reason. The form preview uses `previewSum()` (integer cents) for display only.

**A savings deposit leaves the balance.** `add_to_savings_goal()` also inserts a transaction marked `is_savings` in the caller's *personal* group (never a shared one: goals are private) — an expense for a deposit, an income for a withdrawal, titled with the goal's name, dated with the device's `p_occurred_on`. `period_summary()` and `filtered_totals()` return `income` and `expense` without these rows and a separate `savings` (net deposits); `balance` still counts everything. They have no category, so `category_breakdown()` and `budget_totals()` skip them on their own. Only that function writes them: clients hold no privilege on `is_savings` / `savings_goal_id` (it is `SECURITY DEFINER` for that reason and checks goal ownership itself), and `guard_savings_movement()` refuses a direct update or delete at trigger depth 1. `is_savings` exists because `savings_goal_id` goes `NULL` when a goal is deleted, which would have turned past deposits into uncategorised expenses; deleting a goal leaves its rows as savings and does not refund the balance. Amounts saved before this change (migration `20260925000200`) have no transaction.

**Every transaction belongs to a wallet** (`wallets`, migration `20260926000100_wallets.sql`): cash, mobile money, bank. Each group has exactly one `is_default` wallet, created by the `budget_groups_create_default_wallet` trigger on every group insert (signup and `create_shared_group()` included, without touching either function) and never deletable. A transaction inserted without `wallet_id` — any write from an app build older than wallets, and the movements written by `add_to_savings_goal()`, `create_debt()`, `confirm_recurring()` — lands in the default wallet through `assign_transaction_wallet()`, which also refuses a wallet from another group. The migration moved the history into each group's default wallet with `disable trigger user` around the update, so no row was marked « modifié » and nothing reached the activity log; reuse that pattern for any future backfill. A wallet balance is `opening_balance` + incomes − expenses + transfers in − out, summed by `wallets_overview()`; `opening_balance` is a starting point, not an income, and « Ajuster au solde réel » (`adjust_wallet_balance()`) shifts it by the gap instead of inventing a transaction. `wallet_transfers` move money without changing the group balance; `transfer_between_wallets()` turns a fee into a real expense in the « Frais mobile money » category on the source wallet. Transfers are never deleted — a mistake is undone by a reverse transfer. The wallet FKs are plain `no action`, not `restrict`: a group deletion cascades into wallets and transactions in an order Postgres picks, and `restrict` failed when the wallet went first; `guard_wallet_delete()` gives the friendly refusal instead. In the app, the wallet picker only appears when the group has more than one wallet, above the categories (picking a category dismisses the keyboard and reveals « Enregistrer »), preselected with the last wallet used in the group (`readLastWallet`). Keys `wallets` / `transfers` nest under `['transactions']`.

**Every money movement takes a wallet, not only a plain entry** (migration `20260928000200`): `create_debt()`, `record_debt_payment()`, `confirm_recurring()` and `add_to_savings_goal()` gained a trailing `p_wallet_id default null` (NULL = the group's default; `assign_transaction_wallet()` still refuses a foreign wallet). The functions were dropped and recreated, and a call from an older app still resolves because the new parameter is last and defaulted. A recurring template remembers the wallet of its first occurrence (`recurring_transactions.wallet_id`, checked by `check_recurring_wallet()`, `on delete set null`); the one-tap confirmation on the Synthèse uses it, the `recurring` sheet can override it for one occurrence. Savings deposits pick among the **personal** group's wallets, whichever group is active. Every sheet goes through `useWalletChoice(groupId, initial?)` — `undefined` = creation, preselect the last wallet used; a value or `null` = start from existing data — so none preselects differently from the others; its selection is derived at render, because a template's wallet can arrive after the first render.

**Loans and debts move the balance on their own line** (`debts`, migration `20260925000600_debts.sql`). A « loan movement » is a transaction with `debt_id` **and no category**: that is what `period_summary()` / `filtered_totals()` put on the `debts` line. A debt belongs to a group, like a transaction; `counterparty` is free text, not an app user. Every money movement is a transaction carrying `debt_id`: `create_debt()` writes the debt and its first movement (lending is an expense, borrowing an income), `record_debt_payment()` writes a repayment in the opposite direction and refuses more than what remains. Both are `SECURITY DEFINER` because clients hold no privilege on `transactions.debt_id` (nor any insert on `debts`), and both check group membership themselves; ids come from the app, so a replay returns the existing row. `period_summary()` and `filtered_totals()` keep these rows out of `income` / `expense` and return them as `debts`, signed like an income, so `balance = income − expense − savings + debts`. What remains owed is never stored: `debts_overview()` and `debts_totals()` sum it in Postgres. Unlike a savings goal, `debt_id` cascades on delete — deleting a debt means it was entered by mistake, so its movements leave the balance; `guard_debt_movement()` blocks editing or deleting a movement from the history (trigger depth 1 only, so the cascade passes). App keys `debts` / `debtTotals` nest under `['transactions']`, since the remainders derive from transactions.

**A credit sale is a third debt direction, `credit_sale`** (migration `20260928000200`): the merchant sold on credit, the customer owes. `create_debt()` writes no transaction for it — nothing enters the till on the day of the sale —, and each `record_debt_payment()` is an income carrying both `debt_id` and the « Commerce » category, so it counts as revenue (and in `commerce_summary()`), not on the loans line. `debts_overview()` counts a credit sale's payments like a loan's (incomes); `debts_totals().owed_to_us` includes customers, and the debts screen lists them under their own heading. The former check `transactions_debt_uncategorized` became `transactions_debt_not_savings`.

**Budgets are monthly or weekly.** A `weekly` budget compares to the current week, Monday to Monday exclusive (`weekBounds()`, computed on the device like `periodBounds()`); `useBudgetProgress()` reads a second `category_breakdown` over the week only when such a budget exists, and `budgetProgress()` picks the slices by `budget.period`. `budget_totals()` sums **monthly budgets only** — a weekly and a monthly ceiling don't add up to any period — so each weekly budget stands on its own card, labelled « cette semaine ». `queryKeys.categoryBreakdown` carries `to` as well as `from` since then: a week starting on the period's first day would otherwise share its cache entry.

**Recurring transactions are proposed, never recorded on their own** (`recurring_transactions`, migration `20260925000500`). A template belongs to a group, like a transaction; when `next_due_on` reaches the device date, `DueRecurring` shows it at the top of the Synthèse to confirm or skip. `confirm_recurring()` inserts the transaction with an app-drawn id (a replay returns the existing row) and advances the template; both it and `skip_recurring()` take the due date the caller saw and refuse — or, for a skip, ignore — one another member already handled. Both are `SECURITY INVOKER`: transaction and template policies apply as written. `anchor_day` is 1–28 for monthly, ISO weekday for weekly, and a check constraint pins `next_due_on` to it; `src/lib/recurrence.ts` (Jest) and `next_recurrence()` (pgTAP) compute the same dates. The rhythm is not updatable — delete and recreate. Templates are created from the transaction form (« Répéter », create mode and online only: recurring writes don't queue offline) and managed from `recurring-list` / the `recurring` sheet, where the amount entered applies to that occurrence only. `queryKeys.recurring(groupId)` sits outside `['transactions']`; a confirmation invalidates both roots. The table is in the Realtime publication so a member's confirmation clears the others' list.

`queryKeys.budgets(groupId)` sits outside `['transactions']`, unlike
`periodSummary` and `categoryBreakdown`. Those derive from transactions and must
ride their invalidations; a ceiling does not, and nesting it would reload every
budget on each expense entry. `queryKeys.budgetsAll()` is the `['budgets']` root
above it, and exists only for invalidation: a mutation or a Realtime event may
land after the active group has changed, so invalidating the per-group key would
target the wrong group. Reads use `budgets(groupId)`; invalidation always goes
through the root.

Anything *derived* from transactions nests under that same root — `periodSummary(groupId, from)` is `['transactions', 'summary', …]`. It rides the existing invalidations from the mutations and the Realtime subscription, so neither had to learn it exists. Put new derived caches under the prefix they depend on rather than adding invalidation calls.

`usePersistedQueryCache()` clears the TanStack Query cache when the session's user changes, so a second account signed in on the same device never briefly sees the previous one's cached groups or transactions. It also writes that cache to AsyncStorage (see Offline mode below).

## Offline mode

The app reads and enters expenses without network; the database stays Supabase. Three pieces:

- **The cache survives restarts.** `usePersistedQueryCache()` restores the TanStack Query cache from AsyncStorage under a per-user key (`query-cache:<userId>`) and keeps writing it. The splash waits for the restore on first launch only, so an offline start shows the last known figures, not spinners. Caches of any other user are reduced to their queued writes on every session resolution (`queueOnly()`), so signing out leaves no data read from the server on the device, while writes not yet sent survive and go out at that account's next sign-in; voluntary sign-out warns first when writes are pending. `gcTime` equals `PERSISTED_CACHE_MAX_AGE` (30 days): a query evicted from memory earlier would also vanish from disk. `buster` is the app version plus `CACHE_FORMAT`: a cache written by another version loses its queries but keeps its queued writes (`keepQueueAcrossVersions()`, in the wrapped persister), so installing an update over pending writes doesn't drop them. On the way to disk (`prepareForDisk()`), a write still in flight is recorded as paused — the library only resumes paused mutations at startup, so one sent when Android killed the app was lost — and infinite queries keep only their first `PERSISTED_HISTORY_PAGES` pages. All of this lives in `src/lib/offline-queue.ts` (Jest). **The cache is written by `serializeCache()` (`src/lib/cache-serialization.ts`), never plain `JSON.stringify`**: several reads return a `Map` (`getDailyTotals`, savings `rhythms`, group `byGroup`), which plain JSON writes as `{}`. Restored that way, the Opérations and Épargne tabs crashed on `.get()` at every launch, online or not, until the first build with the fix bumped `CACHE_FORMAT` to 2. Returning a `Map` or `Set` from `src/data/` is fine; any other non-JSON type (a `Date`, a class instance) is not, unless `cache-serialization.ts` learns it.
- **Transaction writes queue.** `onlineManager` is wired to NetInfo (`isConnected !== false`; `isInternetReachable` is deliberately ignored — it pings Google and a false negative would queue writes on a working network). Create/update/delete of a transaction run with `networkMode: 'online'`, so offline they pause instead of failing. **A creation carries an id drawn by the app** (`randomUUID()` from `expo-crypto`, once per open sheet) and is written `on conflict (id) do nothing`: a write that reached the database without its response coming back — replayed after a restart, or re-tapped after « Pas de connexion » — finds its row instead of creating a second one. `do nothing`, not a merge, so a stale replay never overwrites another member's later edit. Their `mutationFn` and effects are registered with `setMutationDefaults` under `mutationKeys` (`src/lib/query-keys.ts`), not passed to `useMutation`: a queued write is persisted and replayed after a restart, when only its key survives. Only those keys are dehydrated, paused or in flight. They share one `scope`, so they run one at a time in the order made, and they retry transport errors (`isTransportError()`, empty `code`) without limit on a growing delay capped at a minute — NetInfo says « connected » on a flapping 2G link while requests fail — but never a refusal from the database. **Every Supabase request has a 20-second limit** (`src/lib/fetch-with-timeout.ts`, passed as `global.fetch`): React Native's `fetch` has none, and on a silent 2G link one request hung forever while the whole queue waited behind it. A timeout, and a gateway status on `/rest/v1/` (408, 429, 502–504, 520–524 — never 500, which PostgREST also returns for SQL errors that would repeat forever and block the queue), are raised as errors whose message `isTransportError()` recognises, so they retry like a lost connection. The sheet closes as soon as a write hits such a failure (`isRetrying`). An update carries `expectedUpdatedAt`, the row version the form opened on; `update()` filters on it and raises `TRANSACTION_CONFLICT` when another member changed the row meanwhile, unless the row already holds the patch (a replay whose response was lost). Two offline edits of the same row follow the versions the session itself produced (`VersionChain`). A delete of a row already gone succeeds. The edit sheet prefills from the list row already in cache (`initialData`), and never opens a form without data: offline, a detail query never fetched is paused, neither loading nor errored in TanStack v5.
- **Debt repayments queue too.** `mutationKeys.recordDebtPayment()` sits under the same `['transactionWrites']` root, so it is persisted, counted by the banner, sent in the same scope and retried the same way; its defaults are registered in `registerTransactionMutationDefaults`. A repayment that became too large meanwhile (another member settled the debt) is refused by the database and raises the queued-write alert. Creating or deleting a debt still fails fast.
- **A queued write the database refuses is kept, not dropped.** The `MutationCache` `onError` turns it into a `RejectedWrite` (`describeRejected()`, `src/lib/rejected-writes.ts`, Jest) stored per account in AsyncStorage (`rejected-writes-store.ts`, 20 at most), and the alert names the entry (« Dépense de 5 000 FCFA d'hier : … »). `RejectedWrites` (« À corriger », above the pending block on the dashboard and the history) reopens a refused creation in the form, prefilled (`/transaction?draft=<id>`, a new id, in its original group if still a member), reopens a refused update, and lets the user drop the rest. A refusal of the recurrence alone (`RECURRENCE_FAILED`) is not stored: the operation itself went through.
- **« Répéter » travels with the entry.** `CreateTransactionInput.recurrence` carries the template (with its own app-drawn id; `createRecurring()` is `on conflict (id) do nothing`), and the create mutation's `mutationFn` writes both. Attached to the screen's `onSuccess`, it was lost whenever the sheet closed on a flapping network.
- **The queue survives the disk.** `rescueExpiredQueue()` keeps pending writes (and drops read data) when the phone's clock makes the cache look older than `PERSISTED_CACHE_MAX_AGE` — the library would otherwise erase queue and all. A failed write to AsyncStorage retries through `removeOldestQuery` (read data only, never mutations) and reports to Sentry once nothing is left to remove; an unreadable cache is reported too.
- **A saved update is written into every cached list at once** (`mergeSavedRow()`, via `setQueriesData` over `['transactions']`) before the usual invalidation, so a restart before the refetch no longer reopens the old version and hits a false `TRANSACTION_CONFLICT`.
- **Everything else fails fast.** The global mutation default is `networkMode: 'always'`, so a budget, savings or group write offline errors immediately with « Pas de connexion » rather than spinning. To make another write queue, give it a `mutationKeys` entry, register defaults for it, and widen `shouldDehydrateMutation` — delta RPCs (`adjust_budget_amount`, `add_to_savings_goal`) are safe to replay as long as the queued variables carry their `p_id`.

The transaction sheet closes as soon as a write is queued. `OfflineBanner`, above the `(app)` stack, says the figures may be stale and counts pending writes; a queued write the database later refuses raises an `Alert` from the `MutationCache`, because no form is left to show it — writes sent immediately keep their inline error only. Queued creations show in a separate « En attente d'envoi » block (`PendingTransactions`, on the dashboard under the balance and at the head of the history), built from the mutation variables by `usePendingTransactions()` and drawn by `TransactionRow pending` — not a link, since there is no id yet. They are deliberately kept out of the list caches and the totals: those are computed in Postgres, and recomputing them client-side would be a second definition of « spend for the period ». Queued updates and deletions are only counted by the banner.

**Form sheets scroll with `SheetScrollView`, never a bare `ScrollView`.** A `formSheet` does not resize when the keyboard opens, so the note field at the bottom of the entry form sat under the keyboard while being typed. `SheetScrollView` adds a keyboard-height spacer after the content and scrolls just enough to lift the focused input (found with `TextInput.State.currentlyFocusedInput()`, so no field needs wiring) above the keyboard; it re-checks after each touch because Android doesn't always fire `keyboardDidShow` when focus moves between fields. No native module.

The banner sits above the stack and shrinks it. It takes the top safe area itself, so while it shows, the `(app)` layout hands the stack a `SafeAreaInsetsContext` whose `top` is 0 (`useOfflineBannerVisible()`). Screens must therefore read their margins with `useSafeAreaInsets()` (as `Screen` does) and never through a native `SafeAreaView`, which measures on its own and put the status-bar height back under the banner. On Android a `formSheet` opens inside the stack's bounds, not the window's, so a sheet capped at a fraction of the window overflowed the bottom and hid its save button. Sheets cap their height with `useSheetMaxHeight()`, which reads the stack height measured by `StackFrameProvider` — never `useWindowDimensions()` directly. `@react-native-community/netinfo` is a native module: it needs a new EAS build (Expo Go already ships it).

`ActiveGroupProvider` holds the active group for the whole app. It reopens on the last group the account chose (`readLastGroup(userId)`, AsyncStorage, per account — a tontine viewer reopening on their empty personal account believed the treasury was empty), falling back to the personal account (first in the membership list) when there is no choice or the group was left. `isLoading` stays true until the stored choice has been read, so the dashboard never flashes the personal figures first. Screens write into that group; they never pick a `group_id` themselves.

Data errors are mapped by SQLSTATE code in `src/lib/data-errors.ts` first — that rule doesn't change — with two message-based exceptions. One is a fallback for transport failures only, which reach the client as an object with `code: ""` and no SQLSTATE to key off. The other is deliberate: `error.code === 'P0001'`, the generic code every bare `raise exception` shares (`join_group_with_code()` and the guard triggers all raise through it), returns `error.message` verbatim rather than going through `MESSAGES`, because a single table entry keyed on `P0001` can't represent several unrelated messages that all happen to share that code. Same priority order as `auth-errors.ts`.

**The history filters live once in SQL, in `filtered_transactions()`** (migration `20260928000200`): period, type, several categories (`p_category_ids`), wallet, tag, search. `daily_totals()`, `filtered_totals()` and `filtered_category_totals()` (the PDF statement's per-category subtotals) all aggregate its rows, and `filterArgs()` in `src/data/transactions.ts` is the one place that turns `TransactionFilters` into their arguments; `listPage()` expresses the same predicate in PostgREST. The old single `p_category_id` stays accepted for older apps. `TransactionFilters.categoryIds` is sorted and `null` rather than empty, so the cache key doesn't depend on tap order. The wallet chip only shows with several wallets, the tag chip only once the group has used one.

**Tags are a `text[]` on the transaction** (`transactions.tags`, GIN-indexed, checked by `tags_are_valid()`: ≤ 5, 1–30 chars, trimmed, no case-insensitive duplicate), not a table: the row and its tags go in one write, so the offline queue needed nothing new. Renaming a tag everywhere is therefore not possible. `src/lib/tags.ts` (Jest) normalises input and reuses the spelling of a tag the group already has (`transaction_tags()`), because the history filter matches a tag exactly. A write queued before tags has no `tags` field: creation writes `[]`, update leaves the column alone, and `patchIsApplied()` skips the comparison.

History pages are **cursor-paginated on `(occurred_on, id)`**, never `OFFSET` / `.range()`. Realtime inserts rows while the user scrolls, so an offset shifts every later page: a row appears twice, or is skipped. `transactions_group_occurred_idx` and the `id` tiebreak exist for exactly this. PostgREST cannot express row-value comparison, so `listPage()` builds the equivalent predicate with `.or()`; the cursor values always come from a row the server already returned.

## RLS

Security lives in the database, not the client. Every policy resolves to "is the caller a member of this group?".

Policies decide *which rows*; column privileges decide *which columns*. `authenticated` may read only `users.id`, `display_name`, `avatar` and `created_at` (migration `20260926000300_hide_member_emails.sql`): `users_select_self_or_covisible` used to hand co-members each other's email. The app takes the user's own email from the session, never from `users`. `authenticated` may update only `users.display_name`, `budget_groups.name` / `period_start_day` and `categories.name` / `icon` (a category moved to another group or switched to the other type would drag its transactions along) — without that, `users_update_self` let a user rewrite their own `users.email` (desynchronising it from `auth.users`) and `budget_groups_update_owner` let an owner change `owner_id` or `is_personal` through a direct API call. A new writable column needs its own `grant update (col)`, or the app gets `42501`. Free text is bounded in the database as well as in the app: `transactions.note` ≤ 120 (like debts, transfers and recurring templates — a repeated operation hands its note to its template), `savings_goals.name` ≤ 60 (it becomes a deposit's note), `users.display_name` ≤ 64 (`handle_new_user()` falls back on the email's local part), `budget_groups.name` ≤ 60, all `not valid` so older rows don't block the migration. The app caps input shorter, in `src/lib/validation.ts`. A `SECURITY DEFINER` function that returns an existing row on replay checks group membership before returning it (`create_debt()`, `record_debt_payment()`, `transfer_between_wallets()`). `transactions` grants every column except `is_savings` and `savings_goal_id` (see savings above); its frozen columns stay granted on purpose, so `guard_immutable_columns()` keeps refusing them with a message naming the column.

`is_group_member()` / `is_group_owner()` / `shares_group_with()` are `SECURITY DEFINER` **on purpose**: a policy on `account_memberships` that queries `account_memberships` recurses infinitely. Keep new membership-dependent policies going through these helpers.

That reason does not generalise. `period_summary()` is `SECURITY INVOKER`, because it reads `transactions` from outside any policy — no recursion, so `transactions_select_member` applies as written and there is no bypass to audit. A non-member sums zero rows and gets `0/0/0`, which is an answer, not an error. Copying `DEFINER` by imitation is the mistake to avoid.

`savings_goals_all_own` is the one policy in the project that resolves on `user_id = auth.uid()` instead of group membership, and that is deliberate, not an oversight: a savings goal stays personal even inside a shared budget — two members of the same group never see each other's goals, which `supabase/tests/savings_goals_rls_test.sql` proves. Do not "fix" this policy to route through `is_group_member()`; doing so would silently share a shared budget's savings goals across its members. For the same reason `queryKeys.savingsGoals()` is a single flat key, deliberately not split per group — `usePersistedQueryCache()` is already the only boundary that matters here, unlike `budgets`, which has an active group to track.

Aggregates are computed in Postgres, never in JavaScript: amounts are `numeric(12,2)`, which Postgres sums exactly, while JS addition goes through binary floats. PostgREST's own aggregate functions are not an option — enabling them requires `pgrst.db_aggregates_enabled` on the `authenticator` role, which opens `sum()` on every table for every client.

Joining a group goes through the `join_group_with_code()` RPC, not a direct insert — the joining user cannot yet read the group's invitations. Creating a shared group goes through `create_shared_group()`, a `SECURITY DEFINER` RPC that inserts the group and its owner-membership row atomically. **Clients have no `insert` or `update` privilege on `account_memberships` at all** (migration `20260925000100_harden_group_access.sql`): the former `account_memberships_insert_owner` policy checked only that the caller owned the group, so any user could create a group and enrol someone else in it — who then became co-visible and leaked their email. Only `SECURITY DEFINER` functions write memberships (`handle_new_user()`, `create_shared_group()`, `join_group_with_code()`, `set_member_role()`, `transfer_ownership()`); `delete` stays open (exclusion and leaving).

**Invitation codes are generated and bounded by the database.** `generate_invitation_code()` draws 8 symbols from `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (no 0/1/I/O), and `expires_at` defaults to 7 days; clients may insert only `group_id`, `created_by` and `role` (`member` or `viewer`, never `owner`), and update only `revoked_at`. **There is one active code per role** (`getActiveInvitation(groupId, role)`, `queryKeys.groupInvitation(groupId, role)`): switching the role in the group screen shows that role's code and revokes nothing, so a viewer code already posted on WhatsApp keeps working. The screen defaults to **viewer**, the safe choice. A code serves everyone who receives it until it expires or is revoked; `used_at` / `used_by` only keep the last use, and a code for another role is another code. `join_group_with_code()` normalises the input (uppercase, no dash or space), enrols with the invitation's role without ever changing an existing member's, returns `NULL` — not an exception — for an unknown, revoked or expired code, and refuses after 10 misses per user per hour, counted in `invitation_attempts` (no client privilege) under a per-user advisory lock. It returns `NULL` because an exception would roll back the recorded attempt; `joinGroupWithCode()` turns it into an `INVITATION_REJECTED` error that `data-errors.ts` maps. **Viewers cannot read codes** (`group_invitations_select_writer`, migration `20260929000100`): a viewer could otherwise read a `member` code, leave, and rejoin with write access; members still read them, to invite their relatives. For the same reason `revoke_invitations_on_member_change()` revokes every active code when the owner excludes someone, and the active `member` codes when a member is demoted to viewer; a voluntary departure (`old.user_id = auth.uid()`) revokes nothing. A test that simulates a member leaving must therefore set that member's claims before the delete, or the trigger reads it as an exclusion. New tables in `public` receive Supabase's default grants to `anon` and `authenticated`: revoke them explicitly when a table is meant to be reached only through functions.

**Invitations travel as a link.** The shared message carries `https://canteuf.github.io/WazuFinance/join/?code=…` (`invitationLink()`), because WhatsApp doesn't linkify a custom scheme. That page, `docs/join/index.html`, is published by GitHub Pages from the `docs/` folder of `main` (repository settings → Pages); it validates the code with the same alphabet and opens `wazufinance://join/CODE` — through an `intent://` URL on Android, which falls back to the Play Store when the app is missing. In the app, `src/app/+native-intent.tsx` catches that path, stores the code (`pending-invite.ts`, one hour at most) and opens `/`; `usePendingInvite()`, mounted in the `(app)` layout, then pushes `group-join?code=…` pre-filled. A `join/[code]` route would not do: signed out, the root guards make it unreachable and the code would be lost during sign-up. Expo Go answers to `exp://`, not `wazufinance://`: the link only opens a built APK.

`guard_owner_orphan()` (the trigger on `account_memberships` added by migration `20260911000100_group_management.sql`) blocks an owner from leaving or being demoted while the group has other members and no other owner, using `pg_trigger_depth() = 1` so only a direct client action is blocked — every cascade (group deletion, account deletion) runs nested at a greater depth and passes through unblocked.

**Three roles: `owner`, `member`, `viewer`** (migrations `20260927000100` / `000200`). A viewer reads the whole group and writes nothing — the tontine model: the treasurer keeps the books, everyone else follows them. There is no separate treasurer role or group setting; a tontine invites its members as viewers. The rule lives in `guard_viewer_write()`, a `BEFORE INSERT OR UPDATE OR DELETE` trigger on `transactions`, `budgets`, `debts`, `wallets`, `wallet_transfers`, `recurring_transactions` and `categories`, not in the policies: one place covers direct writes *and* the `SECURITY DEFINER` functions that bypass RLS (`create_debt()`, `transfer_between_wallets()`…), and it raises a `P0001` message the app shows verbatim. It fires at `pg_trigger_depth() = 1` only, so cascades pass. `is_group_viewer()` is `SECURITY DEFINER` like the other membership helpers. The app hides every write entry point through `useCanWrite()` (FABs, row links, budget cards, debts, wallets, due recurring items) and shows `ViewerNotice` on the dashboard — the screens follow the database, never the reverse. Roles change only through `set_member_role()` (owner only, member ↔ viewer) and `transfer_ownership()`, which promotes the target, then demotes the caller, then moves `budget_groups.owner_id` — the column account deletion cascades on, so leaving it on the former owner would let their deletion take the group with it.

Account deletion therefore can't rely on that trigger, and doesn't: it goes through the `delete_own_account()` RPC (migration `20260919000100_account_settings.sql`), which refuses with `P0001` while `owned_groups_with_other_members()` is non-empty — the same function the settings screen reads to disable its button, so the screen and the database share one definition of "what blocks deletion". It is `SECURITY DEFINER` for its own reason: clients have no right on `auth.users`, while `postgres` holds `DELETE` on it without being superuser (verified on the hosted project), so no Edge Function is needed. **A deleted account's rows in the groups that survive it stay** (migration `20260926000200_departed_member_history.sql`): `transactions`, `debts`, `wallet_transfers` and `recurring_transactions` have a nullable `user_id` with `on delete set null` and an `author_name` column that `set_departed_author()` fills from the `wazu.departing_name` setting `delete_own_account()` puts in its transaction — the `users` row is already gone when the cascade reaches them. `is_author_departure()` recognises that update, and `guard_immutable_columns()`, `touch_updated_at()` and `log_activity()` let it through without a « modifié » mark or a journal entry; it is `SECURITY DEFINER` so a client can't pass a member who merely left the group for a deleted one. The app shows such a row as « Nom (ancien membre) » (`departedAuthorName()`). The personal group and groups where the member was alone still go whole, through `owner_id`. The client then signs out with `scope: 'local'` — the default global sign-out would call the API with the token of a user who no longer exists and throw after a successful deletion. Deletion done from the Supabase dashboard bypasses the check; only the client escape is closed.

`join_group_with_code()` also refuses a group that has no `owner` membership left: when a sole owner leaves, a still-valid invitation used to let someone into a group nobody could manage. A `for share` lock on the owner's membership closes the race with a simultaneous departure.

## Activity log

`activity_log` records every insert, update and delete on `transactions`, `budgets`, `debts` and `wallets`, every `wallet_transfers` insert, and every `account_memberships` change (join, leave or exclusion, role change, hand-over): who, when, the row before and after (`old_values` is `NULL` for an insert). Skipped on purpose (migration `20260927000300_full_activity_log.sql`): inserts in a personal group — which also keeps the signup transaction free of extra writes —, the first movement of a debt (`create_debt()` writes it in the same transaction as the debt, which already has its entry), and the owner's membership when a group is created. `formatActivity()` turns each subject into a sentence; the people and wallets an entry names come from an `ActivityContext` the screen builds, since the log only stores its author. The whole log exports as PDF (`activity-report.ts`, `useExportActivity()`).

**A member who leaves keeps a name** in `former_members` (group, user, display name and avatar at departure), written by the `remember_former_member()` trigger and erased when they rejoin — a snapshot rather than a wider `users` policy, so someone who left doesn't keep exposing their future name or face. On account deletion the name comes from `wazu.departing_name`. Row authors, the export's « Saisie par » and membership entries in the log all fall back on it (`useFormerMembers()`, key nested under `groupMembers(groupId)` so the memberships Realtime invalidates it). It is written only by the `log_activity()` trigger. Clients hold `select` and nothing else — no policy and no privilege for insert, update or delete — so no client can add, rewrite or erase an entry, including through a direct API call.

`log_activity()` is `SECURITY DEFINER` for its own reason, not by imitation of the membership helpers: it inserts into a table where clients deliberately have no write right. Two guards keep it from breaking cascades, and both are covered by `activity_log_test.sql`:

- it writes nothing when the row's group no longer exists — deleting a group or an account cascades into transactions and budgets, and an entry pointing at a deleted group would fail its foreign key and roll the whole deletion back;
- it reads the author from `users` rather than taking `auth.uid()` as is — when users delete their own account, their `users` row is already gone during the cascade.

To journal another table: one `create trigger … execute function public.log_activity('<subject>')` and one more value in the `activity_subject` enum.

`updated_at` moves only on a real change: `touch_updated_at()` compares the row with and without `updated_at`, and ignores any value the client sends. That is what makes « modifié » (`updated_at > created_at`) trustworthy. `log_activity()` uses the same comparison, so the mention and the log always agree.

`transactions.id`, `transactions.user_id`, `transactions.group_id`, `transactions.created_at`, `budgets.id`, `budgets.group_id`, `budgets.category_id` and `budgets.created_at` are frozen: `guard_immutable_columns()` raises `42501` on any change. The app never edits them; the update policies alone did not prevent it. Without this guard, a member could advance `created_at` past `updated_at` through a direct API call and erase the « modifié » mention.

On the app side, `queryKeys.activity(groupId)` sits outside `['transactions']` and has no Realtime subscription on purpose. The feed is read deliberately: it refetches on every open (`refetchOnMount: 'always'`) and on pull-to-refresh, because a list that shifts under the finger while being read is worse. Pages are cursor-paginated on `(occurred_at, id)` like the history. The cursor keeps the timestamp string exactly as PostgREST returned it: a round trip through `Date` drops the microseconds, and the next page would repeat or skip an entry.

## V1 scope (decided — do not re-litigate)

In: manual transaction entry, per-category budgets with in-app visual alerts, savings goals, CSV/PDF export (after the main screens, before notifications).

Out, with reasons:

- **Bank connection** — needs an aggregator (Plaid / Powens), PSD2 compliance, recurring API cost. Separate project after V1 is validated by usage.
- **Multi-currency** — no identified need (the single currency is XAF, see Core data model); adding a `currency` column to `transactions` and `budgets` later is cheap, so don't complicate the schema now.
- **Push notifications** — needs Expo Notifications, iOS/Android permissions, and a Supabase edge function checking thresholds. In-app alerts suffice for V1.

## UX constraints that shape the code

- **The theme choice goes through `Appearance.setColorScheme()`, not a theme provider.** `src/lib/theme-preference.ts` stores `system` / `light` / `dark` in AsyncStorage; the root layout reads and applies it before hiding the splash, so the first screen never flashes the phone's theme. `useColorScheme()` then returns the forced value everywhere — `useColors()`, the navigation theme and native components follow without knowing the setting exists. `system` (the default) maps to `'unspecified'`, which hands control back to the phone. React Native Web doesn't implement the override: on web the app follows the browser.
- **The theme change is a cross-fade of a screenshot, not an animation of colours.** `useColors()` returns static palettes read at render, so no component can tween between two themes. `ThemeTransitionProvider` (root layout) photographs its content with `react-native-view-shot`, mounts the photo on top, lets the theme change underneath, then fades the photo out. A plain veil was tried first and shows one flat all-dark or all-light frame. The sequencing and its races — two quick choices, a slow capture, an image that never loads — live in `src/lib/theme-transition.ts`, covered by Jest with fake timers, and every wait has a watchdog: a stuck photo would freeze the screen on the old theme with nothing to say so. When the capture fails (a build without the native module) the theme changes without a fade; the fade is never a condition of the change. `react-native-view-shot` is a native module, so it needs a new EAS build, but Expo Go already ships it. Native `formSheet` presentations sit above the root and are not covered.
- **Font scale is followed, not capped.** System font scaling grows text without growing its container, so containers must widen or reflow: derive sizes from `useWindowDimensions().fontScale` (it re-renders on change, unlike `PixelRatio.getFontScale()`), and stack two-column rows past `stackAtFontScale`. Only two places cap it — `AmountInput` and the dashboard balance — because their available width is the screen itself.
- **A `<Link asChild>` child's `style` must be `StyleSheet.flatten(...)`, never an array.** `asChild` renders through a `Slot`, which throws a render error on an array style — and only in development, so `npx expo export` (a production build) passes without a word, as do tsc, lint and Jest. The failure surfaces on a device running the dev bundle, which is the last place the project checks. Every `asChild` site flattens; keep it that way.
- **`categoryGridLayout()` estimates label widths per character, so the tile itself carries the fallback — and the fallback differs by label.** The grid picks its column count from `CHAR_WIDTH_RATIO = 0.55`, which on a thirteen-letter word like « Remboursement » lands within a point of the real width, close enough to keep one column too many. A multi-word label absorbs that on a second line; a single word has nowhere to break and Android splits it mid-letter (« Rembourseme / nt »). `CategoryPicker` therefore branches: multi-word labels keep `numberOfLines={2}`, single words take `numberOfLines={1}` plus `adjustsFontSizeToFit` and shrink instead. **`adjustsFontSizeToFit` is ignored on Android whenever `numberOfLines > 1`** — pairing it with two lines is a no-op, which is why the branch exists rather than one shared setting. `labelStacked` needs `alignSelf: 'stretch'` for the same reason: in a column, `flexShrink` governs height, so without it the label has no bounded width to shrink against. Tightening the grid threshold instead was tried and reverted twice: « Alimentation » clears three columns by one point, so any margin costs the whole grid a column and breaks the mockup's two-then-three shape (three Jest cases pin it).
- **Expense entry in ≤3 taps** from the main screen (amount, category, confirm). Retention depends on it — it drives navigation and form design. `Screen`'s optional `floatingAction` renders outside the `ScrollView`, pinned in place, so a lengthening list can't scroll it out of reach. In `TransactionForm`, « Enregistrer » sits right under the category grid, and picking a category calls `Keyboard.dismiss()` so the button is visible; date and note fold into a toggle below it, open by default only when editing a row whose values differ from today / no note.
- **A sheet that closes on save confirms through `useToast()`** (`ToastProvider`, around the `(app)` stack so it outlives the sheet): a short message, announced with `announceForAccessibility`, plus a success haptic (`expo-haptics`, native — Expo Go ships it). Queued offline writes get an `info` toast saying they will be sent later. The toast takes no touches (`pointerEvents="none"`), so it can never block the floating action.
- **In a shared group, each transaction row shows its author** (small avatar + name, « Vous » for the current user) through `useTransactionAuthor()`. It reads the `groupMembers` cache without `useGroupMembers()`'s `refetchOnMount: 'always'`, which would refetch once per row.
- **A row's accessibility label carries everything the row shows**: title, category, « Dépense / Revenu de … francs CFA », date, author, « modifiée ». `ProgressBar` is a `progressbar` with a value text that names the status, and budget warnings pair the colour with an icon and a word. Touch targets are at least 44 points.
- **Light-theme `primary` and `positive` are `#08775A`** (5.5:1 under white text, 4.9:1 as text on `background`). The original `#0EA47A` failed AA under white text; check both uses before changing it.
- Transaction history must be paginated (`transactions_group_occurred_idx` covers the filter + sort).
- Forms default to smart values: last-used type and category (per group, `last-used.ts`), today's date — all editable, just pre-filled to save a tap. They are remembered in `onMutate`, when the entry is made, not when the server accepts it: offline, the next sale otherwise started from yesterday's choice. A replayed queued write skips `onMutate`, so it never overwrites a newer preference.
- **Input fields use `colors.inputBorder`, never `colors.border`.** `border` separates cards and rows and stays faint (1.3:1); a field outline must reach 3:1 against the field, the page and `surfaceMuted` (WCAG 1.4.11). `TextField` puts its error in the input's accessibility label and announces it through `accessibilityLiveRegion`.
- Shared budgets sync live via Supabase Realtime (`transactions`, `budgets`, `account_memberships`, `budget_groups` are in the publication; a `budget_groups` update — period start day, name — invalidates the memberships query). Transaction events are batched over `REALTIME_BATCH_MS` into one invalidation, since each one refetches every displayed page.
- **A wrong phone clock is reported, not corrected.** Dates, periods and due dates are computed on the device; `AuthProvider` measures the gap between the phone and the `iat` of each freshly issued token (`src/lib/clock.ts`), and `OfflineBanner` asks the user to fix the time beyond five minutes. The lock screen caps a lockout at its normal length when the clock went backwards. `savings_goals` is in the same publication for a different reason — it keeps one user's own devices in sync, never fellow group members, since goals are personal (see RLS above).

## Wording

The app says **opération** (never « écriture », « livre de comptes », « Débit / Crédit »), **dépense / revenu**, and **budget** for a per-category ceiling (never « enveloppe », including in SQL messages the app shows verbatim). The floating action reads « Ajouter ». Code identifiers may keep older names (`ledger`, `envelopes.sql`); only user-facing text follows this rule.

## Conventions

- File names kebab-case; components PascalCase.
- **Comments are never hard-wrapped.** One paragraph is one physical line, however long — `//`, `/* */` and `{/* */}` alike. `.vscode/settings.json` sets `editor.wordWrap: "on"`, so the editor folds them to the window width; re-wrapping them by hand at ~80 columns undoes that, and turns a one-word edit into a diff spanning every line of the paragraph. A blank line still separates paragraphs, and bullets, JSDoc tags and indented code samples keep their own lines.
- User-facing strings in French, code identifiers in English. SQL comments in French, matching the spec.
- Supabase errors are mapped to French text by code in [src/lib/auth-errors.ts](src/lib/auth-errors.ts) — map codes, never message strings, which change between versions.
- TypeScript strict, no `any`. `src/types/database.ts` is **generated** — never edit it by hand. After any migration, run `npm run db:types`, never `supabase gen types … > src/types/database.ts`: the redirection drops the header comment and the enum aliases the app imports, and under PowerShell it writes UTF-16, after which tsc sees no exports at all. [scripts/gen-db-types.mjs](scripts/gen-db-types.mjs) captures the output instead, re-attaches both, and writes UTF-8. A new enum in a migration is added to its `ALIASES` block.
