# Audit du 26 septembre 2026 — corrections à appliquer

Document de reprise : il donne le contexte et la liste des corrections issues du deuxième audit de Wazu Finance, pour poursuivre le travail dans une nouvelle conversation. CLAUDE.md reste la référence pour l'architecture et les conventions : le lire en premier.

## Contexte

App de budget multi-utilisateurs, Expo SDK 57 + Supabase, pour la zone CFA (XAF, montants entiers). Tout le travail précédent est commité et poussé sur `main` :

| Commit | Contenu |
| --- | --- |
| `01f8ab0` | Priorité 1 du premier audit : accès aux groupes, doublons, épargne hors solde, mot de passe oublié par code, CI |
| `249c1e5` | Priorité 2 : catégories régionales, auteur des opérations, partage, vocabulaire, accessibilité |
| `e8b8c53` | Opérations récurrentes (proposées puis confirmées), budgets hebdomadaires |
| `77351c3` | Prêts et dettes |
| `ffb96dc` | Portefeuilles (espèces, mobile, banque), transferts avec frais |
| `12128f1` | Verrouillage par code + empreinte, session dans SecureStore en morceaux, `allowBackup: false`, Sentry, EAS Update |

### Façon de travailler

- Claude code puis vérifie : `npx tsc --noEmit`, `npm run lint`, `npx jest` (265 tests), `npx supabase test db` (pgTAP, Docker Desktop requis, après `npx supabase db reset --local`), `npx expo export --platform android` (bundle).
- L'utilisateur lance lui-même `npx supabase db push` puis `npm run db:types`, et teste dans Expo Go sur Android.
- Commit + push sur `main` seulement quand l'utilisateur dit « C'est bon, commit et push ». Messages de commit en français, sans accents dans le titre.
- Les choix de conception sont proposés avec AskUserQuestion, option recommandée en premier.
- Textes de l'app en français ; commentaires jamais coupés à la main (un paragraphe = une ligne).
- Routes typées : une nouvelle route exige `CI=1 npx expo start --offline --port 8095` (attendre `.expo/types/router.d.ts`), puis arrêter le processus du port 8095 via PowerShell (`Get-NetTCPConnection -LocalPort 8095` + `Stop-Process`). Le port 8081 est celui de l'utilisateur.
- `npx expo install` échoue avec EALLOWSCRIPTS : lire les versions dans `node_modules/expo/bundledNativeModules.json` et les installer avec `npm install`.
- Prettier n'a pas de configuration dans le projet : l'appeler avec `--single-quote --print-width 100 --trailing-comma es5`, sinon il passe aux guillemets doubles.

### État en attente

- Un nouvel APK est nécessaire pour que Sentry, EAS Update et la session dans SecureStore existent sur le téléphone. Les builds EAS du mois sont épuisés (attendre le renouvellement ou compiler en local).
- Le DSN Sentry (région DE, `ingest.de.sentry.io`) est dans `.env` et dans les variables EAS des trois environnements.

## Le deuxième audit

Six agents, chacun avec un rôle métier, ont lu le code : une commerçante du marché de Douala, une trésorière de tontine, un chef de famille aidé par un frère de la diaspora, un responsable conformité (DPO), un ingénieur QA terrain, un responsable produit croissance. Leurs références de lignes n'étaient pas toujours exactes ; les points marqués **vérifié** ont été confirmés dans le code.

## Priorité 1 — Fiabilité et confiance

### 1.1 Saisies hors ligne perdues sans avertissement — vérifié

- `src/hooks/use-persisted-query-cache.ts` : `shouldDehydrateMutation` n'écrit que les mutations `isPaused`. Une écriture en cours d'envoi n'est plus sur le disque : si Android tue l'app à ce moment (téléphone à 2 Go), la saisie disparaît. Persister aussi les mutations en cours des clés `mutationKeys`.
- Le `buster` contient la version de l'app : une mise à jour du Play Store avec des saisies en file les jette. Le commentaire qui dit le contraire est faux. Garder la file à travers une mise à jour (n'invalider que le cache des requêtes), ou au minimum avertir.
- `discardOtherCaches(null)` à chaque déconnexion supprime aussi les saisies en file (déconnexion volontaire, 10 échecs du code, « code oublié »). Avertir avant une déconnexion avec des saisies en attente, et ne pas les perdre en silence.
- Pas de `retry` explicite sur les mutations de transaction : sur un réseau 2G qui vacille (NetInfo dit « connecté », le fetch échoue), la saisie part en erreur et est retirée. Ajouter un `retry` avec délai pour les erreurs réseau (code vide), jamais pour un refus de la base.

### 1.2 Modification hors ligne qui écrase la ligne — à confirmer sur le téléphone

`src/app/(app)/transaction.tsx` : hors ligne, la requête de la fiche est en pause (`isLoading` et `isError` faux dans TanStack v5), le formulaire s'ouvre vide sous « Modifier ». L'enregistrer écraserait la vraie ligne (date du jour, note vide, `wallet_id` null). Garder l'écran de chargement tant que `fetchStatus === 'paused'` sans donnée, ou pré-remplir depuis la ligne déjà dans le cache de la liste (`initialData`).

### 1.3 Suppression de compte — vérifié

- `delete_own_account()` (`supabase/migrations/20260919000100_account_settings.sql`) supprime directement les transactions du membre dans les groupes qui lui survivent. Le trigger `guard_debt_movement` voit `pg_trigger_depth() = 1` et refuse : un membre qui a saisi un prêt dans un groupe partagé ne peut plus supprimer son compte.
- Cette même suppression efface l'historique des groupes partagés (une trésorière qui saisit tout emporterait la caisse). `transactions.user_id`, `debts.user_id`, `wallet_transfers` partent aussi en cascade, y compris des remboursements saisis par d'autres. Décider : conserver les lignes avec un auteur « ancien membre » (`user_id` en `set null` + nom figé) plutôt que les supprimer. Question à trancher avec l'utilisateur.
- Ajouter les tests pgTAP : suppression d'un membre ayant dettes, transferts, récurrences dans un groupe survivant ; cascade complète d'un groupe.

### 1.4 Email visible par les autres membres — vérifié

`supabase/migrations/20260904000200_policies.sql:365` : `grant select, update on public.users to authenticated` (l'update a été restreint depuis, pas le select). Avec `users_select_self_or_covisible`, un co-membre lit l'email. Remplacer par `grant select (id, display_name, avatar, …)` et vérifier que l'app ne lit l'email que pour soi (réglages : `auth.users` / session). Mettre à jour les tests pgTAP.

### 1.5 Verrouillage et session — vérifié

- `src/lib/app-lock.ts`, `lockoutRemainingMs` : si l'horloge recule après des échecs, l'attente peut dépasser des mois. Plafonner le reste à `lockoutDelayMs(failures)`.
- `src/lib/secure-session-storage.ts`, `writeChunks` : les morceaux sont réécrits sur place avant le compteur ; une écriture interrompue mélange anciens et nouveaux morceaux, et le commentaire « jamais un mélange » est faux. Écrire dans un jeu de clés alterné (génération A/B) puis basculer un pointeur en dernier.

### 1.6 Doubles comptes par rejeu — vérifié

`add_to_savings_goal` et `adjust_budget_amount` n'ont pas d'identifiant d'idempotence : si la réponse se perd et que l'utilisateur retouche, le delta compte deux fois (et, pour l'épargne, la transaction du solde est créée deux fois). Ajouter un `p_id` tiré par l'app, comme pour les transactions, dettes et transferts.

### 1.7 Autres points relevés (moindre gravité)

- `src/components/dashboard/due-recurring.tsx` : un nouvel UUID à chaque toucher ; après une réponse perdue, l'utilisateur lit « déjà traitée par un autre membre » alors que c'est lui. Tirer l'id une fois par occurrence affichée.
- `update()` (`src/data/transactions.ts`) sans contrôle de version : une modification rejouée hors ligne écrase en silence celle d'un autre membre. Envisager `updated_at` attendu dans le `where`.
- `budget_groups` n'est pas dans la publication Realtime : un changement du jour de début de période n'atteint pas les autres membres avant rechargement.
- Cache persisté : l'historique en `useInfiniteQuery` sans `maxPages`, chaque combinaison de filtres gardée 30 jours ; risque de dépasser les limites d'AsyncStorage Android (6 Mo). Limiter les pages persistées.
- Chaque saisie d'un membre invalide toute la racine `['transactions']` (toutes les pages d'historique rechargées) : coûteux en 2G.
- Horloge fausse du téléphone : dates futures, récurrences dues trop tôt ; jeton considéré valide à tort (erreurs 401).

### Plan de tests terrain proposé (téléphone Android 2 Go)

1. Mode avion puis 2G faible : 5 saisies, aucune perte ni doublon.
2. Forcer l'arrêt de l'app pendant l'envoi d'une saisie en file.
3. Installer une version N+1 par-dessus un APK qui a des saisies en file.
4. Ouvrir en mode avion une opération jamais consultée.
5. Deux téléphones : même récurrence confirmée, même dette remboursée au-delà du reste, même ligne modifiée dont une hors ligne.
6. Versement d'épargne avec coupure réseau juste après le toucher, puis retoucher.
7. Horloge reculée après 5 codes faux ; horloge avancée d'un mois ; retard de 2 h.
8. Verrou : 59 s puis 61 s hors de l'app, invite biométrique, feuille ouverte, 10 échecs avec saisies en file.
9. Suppression de compte d'un membre non propriétaire ayant saisi une dette et un transfert.
10. 5 000 opérations, 20 pages, plusieurs filtres, stockage presque plein, police à 200 %, TalkBack.

## Priorité 2 — Droits dans les groupes partagés

- **Rôle « lecteur »** (valeur `viewer` dans l'enum `membership_role`) : lit tout, ne modifie rien. Aujourd'hui tout membre peut modifier ou supprimer toute opération du groupe (`transactions_update_member` / `transactions_delete_member`) et supprimer un prêt avec ses mouvements (`debts_delete_member`). Choix du rôle à l'invitation.
- **Passation de propriété** : RPC `transfer_ownership(group, new_owner)` en `SECURITY DEFINER` (les clients n'ont aucun `update` sur `account_memberships`) + bouton dans `group.tsx`. Aujourd'hui `guard_owner_orphan()` impose d'exclure tous les membres.
- **Mode « seul le trésorier modifie »** pour les tontines (rôle ou réglage du groupe).
- **Journal d'activité complet** : enregistrer aussi les créations (aujourd'hui `after update or delete` seulement), les dettes, les portefeuilles, les transferts, les adhésions (nouvelles valeurs de `activity_subject`) ; export PDF du journal pour les réunions.
- **Nom des ex-membres conservé** : `users_select_self_or_covisible` masque le nom d'un membre parti ; la colonne « Saisie par » de l'export devient vide.
- **Invitations** : lien `wazufinance://join/CODE` (schéma déjà configuré) avec une page web de secours vers le Play Store ; code utilisable par plusieurs personnes pendant 7 jours (aujourd'hui `used_at` : un code par personne). Ajuster `join_group_with_code()`.

## Priorité 3 — Usages réels (commerce, famille)

- **Portefeuille au choix** pour `create_debt`, `record_debt_payment`, `confirm_recurring`, `add_to_savings_goal` (paramètre `p_wallet_id` + `WalletPicker`). Aujourd'hui tout va au portefeuille par défaut.
- **Filtre et export par portefeuille** dans l'historique (`listPage`, `filtered_totals`, `HistoryFilterState`).
- **Vente à crédit** : un sens de dette qui ne crée aucune transaction au départ, et dont chaque versement devient un revenu « Commerce » lié à la dette. Aujourd'hui « J'ai prêté » enregistre une dépense.
- **Catégorie par défaut « Achat de stock »** et une carte « Commerce ce mois : ventes − stock » calculée en SQL.
- **Relevé PDF** : sous-totaux par catégorie (`category_breakdown` sur les bornes filtrées) et colonne portefeuille.
- **Filtre multi-catégories** et **étiquettes** sur les opérations (« Argent de Jean », « Rentrée 2027 ») pour rendre des comptes et préparer les dépenses saisonnières.
- **Remboursements de dettes en file hors ligne** (clé `mutationKeys` ; `record_debt_payment` refuse déjà un trop-perçu).
- Idées plus lourdes, à garder pour plus tard : tontine hors revenus et dépenses (comme `is_savings`), objectifs d'épargne de groupe, déplacer un plafond d'un budget à un autre, budgets saisonniers avec dates, photo de reçu, concept « cycle de tontine » (ordre de passage, payé / en retard / amendes), transfert entre groupes boutique / maison.

## Priorité 4 — Avant une sortie publique

### Conformité (points juridiques à faire valider par un juriste)

- Aucune politique de confidentialité, CGU ni consentement à l'inscription (`src/app/(auth)/sign-up.tsx`) : **bloquant**.
- Responsable de traitement à désigner ; formalités auprès de l'autorité camerounaise (loi 2024-017) et de l'ARTCI (loi ivoirienne 2013-450).
- Sous-traitants à documenter avec contrats : Supabase (région à vérifier), Sentry (déjà en UE, `de.sentry.io`), Expo/EAS, GitHub (sauvegardes).
- Suppression incomplète : le journal garde `actor_name` et `old_values` (notes comprises) sans limite ; les sauvegardes durent 30 jours ; rien pour effacer les événements Sentry d'un compte. Définir des durées de conservation, une procédure de restauration qui ré-applique les suppressions, un registre des traitements, une procédure en cas de violation.
- Côté code : écran d'information et consentement ; lien vers la politique dans les réglages ; mot de passe d'au moins 8 caractères ; vérifier que la confirmation d'email est cohérente avec l'inscription ; avertir de ne noter que le prénom d'une contrepartie de dette ; export complet des données de l'utilisateur ; purge de `invitation_attempts` ; chiffrer ou réduire le cache hors ligne (en clair dans AsyncStorage).

### Croissance

- **Mesure** : événements produit sans donnée personnelle (`signup_started`, `signup_completed`, `first_transaction`, `invite_shared`, `invite_joined`, `budget_created`, ouverture du jour), dans une table Supabase sans droit client.
- **Premier lancement guidé** en 3 écrans : jour de paie, portefeuille principal, première dépense ; puis une carte « Invitez un proche ». Le texte vide dit « Touchez + » alors que le bouton affiche « Ajouter » (`recent-transactions.tsx`).
- **Inscription allégée** : retirer la confirmation du mot de passe ; connexion Google ; à terme, code par SMS ou WhatsApp.
- **Rituels** sans notifications : bilan de la semaine partageable en image sur WhatsApp (`react-native-view-shot` déjà installé), série de jours.
- **Fiche Play Store** : nom « Wazu Finance – Budget FCFA & Tontine », captures en situation réelle, taille de l'AAB suivie.
- **Monétisation** (après 5 000 actifs) : Premium à 500–1 000 FCFA par mois payé en mobile money ; tester l'intention d'abord.

## Recommandation

Commencer par la priorité 1 : une saisie perdue détruit la confiance plus vite que n'importe quelle fonctionnalité absente. Points 1.1, 1.2, 1.3 et 1.4 en premier ; le point 1.3 demande une décision de l'utilisateur (garder ou effacer les saisies d'un compte supprimé dans les groupes partagés).
